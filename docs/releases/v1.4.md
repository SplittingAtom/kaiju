# Kobe v1.4: Git organizations

Release notes for the people who run Kobe. v1.4 lets a Workspace connect to an organization on a
git host (GitHub, GitHub Enterprise Server, Gitea or Forgejo), lets agents work in its
repositories without ever holding a credential, and lets a project become a **Repo** whose record
is a repository on the host.

The member and admin view of the same changes is the guide's [What's new](../guide/whats-new.md)
page (served at `/docs/whats-new`); the details are in
[Git organizations](../guide/admin/git-organizations.md) and
[Working with git repositories](../guide/for-agents/working-with-git.md). The design is in
[docs/specs/workspace-git.md](../specs/workspace-git.md).

**Before you upgrade:** take a database backup (v1.4 adds eleven migrations, `0248` to `0258` as
numbered when these notes were written), and check that the server's `/tmp` limit
(`server.tmpSizeLimit`, now `8Gi`) fits your nodes' ephemeral storage
([Chart changes](#chart-changes)). Nothing changes for a Workspace until a Workspace admin
connects a git organization.

## What v1.4 adds

- **Git connections.** A Workspace admin connects up to five organizations (one per host and
  organization) in the Team console's **Git** page. The credential is a GitHub App installation,
  or an access token (a fine-grained GitHub token, or a bot account's token on Gitea and Forgejo).
  It is sealed on the server with its own envelope purpose, never returned by an API, never
  logged or audited, and never enters a sandbox, a browser or a model. Connecting tests the
  credential and shows what it may do. Access levels are Off, Read, and Read and write.
- **Git host tools.** Agents get tools from a built-in **git** connector (separate from the Kobe
  connector): list and read repositories, branches, files, pull requests and issues; create a
  branch; create a repository, open a pull request, comment and create an issue, which ask the
  member first. Nothing destructive exists: no deleting, merging, visibility or settings changes.
  New repositories are private.
- **Git in the sandbox.** `git clone`, `fetch` and `push` work for the connected organizations.
  The egress proxy recognises git smart-HTTP, asks the server for a per-repository credential and
  adds it upstream. Pushes need the connection at Read and write and the Contributor role (for a
  Repo, also editor or owner of its project). Another organization on the same host is refused.
- **Repos.** **Convert to repo…** (the project's owner or a Workspace admin) creates a private
  repository and pushes the project's history as git commits. The host's default branch is then
  the record; Kobe mirrors it (at most 500 files, 50 MiB each, 256 MiB in all) every 5 minutes,
  on open, after a push and on **Refresh**. A repository that grows past the limits shows "too
  large to mirror" and keeps its last mirror. Repos show a git icon in the Files panel. When the
  host repository is archived, deleted or disconnected the Repo becomes read-only; admins can
  **Relink** or **Detach** it.
- **Commits to a Repo.** From the **Commit…** dialog or an agent's `commit_project`, Kobe pushes a
  new branch and opens a pull request. **Allow commits straight to the default branch** is a
  per-connection setting, off by default. An agent's commit to a Repo is the approval subject
  `commit_repo`: it always asks and cannot be remembered. In a conversation on a Repo the agent
  also has a real git working copy at `/workspace/.kobe/repos/<slug>`, which is never synced.
- **Commit author.** Commits carry the member's name and Kobe email, with "via Kobe" in the
  committer. A Workspace setting uses `<short id>+<name slug>@users.noreply.<Site host>` instead.
- **Site controls.** In Site console, Settings, **Git connections**: a switch (on by default) and
  a list of allowed git hosts (empty allows any).

## Minimum host versions

Gitea 1.26.0 and Forgejo 15.0.0. Kobe reads `/api/v1/version` when a connection is tested and
refuses older servers with a message naming the minimum. GitHub Enterprise Server is served by
the GitHub adapter with a base URL.

## Credentials to prepare

- **GitHub App:** repository permissions Metadata read; Contents, Pull requests and Issues read
  and write; Administration read and write only if agents may create repositories. No organization
  or account permissions.
- **Gitea and Forgejo token scopes:** `read:user`, `read:organization`, `write:repository`,
  `write:issue`, and `write:organization` only if agents may create repositories.

The per-host checklist is in [docs/install.md](../install.md#git-for-connected-organizations).

## Chart changes

- `server.tmpSizeLimit` (new, default `8Gi`): the size limit of the server's `/tmp`. Convert to
  repo works there (one conversion per replica, about 4 GiB) and the Repo mirror (about 816 MiB per
  refresh, two at once). Keep it at least `7Gi`; the kubelet evicts a pod that passes it. Count it
  in the nodes' ephemeral storage.
- `egressProxy.git` (new): `internalKeySecret` (empty: the chart generates
  `<release>-egress-proxy-internal`; copy it with your other Secrets), request and response
  limits, concurrency and rate limits for git requests per sandbox.
- The egress proxy may reach the server's internal port 8082 (NetworkPolicy).
- A git host on a private address must be in the Site egress ceiling and marked internal
  (`egressProxy.allowedInternalCidrs` or the same-cluster entry), and its range must be in the
  connectors' internal CIDRs, because the server calls the host's API and pushes conversions
  itself.

## Migrations

Eleven migrations, `0248` to `0258`: the `git_connections`, `git_repositories`, conversion, mirror
and commit tables (all team tables with forced row-level security, covered by the cross-team
probe suite), `projects.kind` (`project` or `repo`), the built-in git connector row, and a
backfill of `linked_at`. They add tables and columns only; no existing data is rewritten except
that backfill. The numbers may change if migrations from other branches land first.

## Audit events

`git.connection.created|updated|credential_replaced|removed|test_failed|expiry_notified`,
`git.settings.updated`, `git.repository.created`, `git.branch.created`, `git.pull_request.opened`,
`git.issue.created`, `git.comment.created`, `git.write.attempted|failed`,
`git.project.conversion_requested|retried|failed|abandoned`, `git.project.converted`,
`git.repo.commit_attempted|committed|commit_failed`, `git.repo.relinked|detached`,
`git.repo.mirror_updated|host_state_changed`, and, in the egress audit, each fetch and push
(`egress.connection`, `egress.git_push`). No event
carries a credential, a message, a file name or a branch name.

## Retention

Kobe never deletes or rewrites anything on the git host. A Repo's history lives there, outside
Kobe's retention, erasure and legal hold. Disconnecting deletes only the stored credential. A
member leaving changes nothing on the host.

## Known limits

- No webhooks: a commit made on the host appears in Kobe after the next refresh (within 5
  minutes, or on **Refresh**).
- One branch is mirrored (the default branch); symlinks, submodules and Git LFS are not
  supported; there is no SSH transport.
- Existing repositories cannot be turned into Repos by import. Conversion of a project is the
  only way, except that an admin may convert into an existing empty private repository.
- Token connections cannot be narrowed per use; the token's own scope is the limit. Protect
  default branches on the host: Kobe does not parse pushes to enforce branch rules.
- Repo reads follow the project's read rule. Every Workspace member is currently an implicit
  reader of every project, so this refuses no member yet.
- Conversion and mirror notices use the Files panel and email; there are no bell notifications.

## Upgrade steps

1. **Back up** the database ([backup and restore](../backup-restore.md)).
2. **Check `server.tmpSizeLimit`** and the nodes' ephemeral storage.
3. **Upgrade** with your values file as for any release (`helm upgrade <release> ... -f
<your values> --wait`) and follow the migration Job's log.
4. **Copy the new Secret** `<release>-egress-proxy-internal` with your other Secrets, unless you
   named your own with `egressProxy.git.internalKeySecret`.
5. **For a self-hosted git host,** add it to the Site's egress ceiling, mark it internal if it is
   on a private address, and ask the Workspace admin to connect it
   ([Git organizations](../guide/admin/git-organizations.md)).
6. Optionally limit the hosts in Site console, Settings, Git connections.
