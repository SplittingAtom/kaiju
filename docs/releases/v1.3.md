# Kobe v1.3: Semantic Memory

Release notes for the people who run Kobe. v1.3 adds **memories**: short statements Kobe knows
about a person, a workspace and the site, given to the agent at the start of every run, learned
from conversations only after a person reviews them, and shared across the team wall only through
a Team admin. Notes (the `remember` and `recall` files of earlier releases) are unchanged.

The member and admin view of the same changes is the guide's
[What's new](../guide/whats-new.md) page (served at `/docs/whats-new`); the details are in
[Memory](../guide/memory.md). Each change below also has an upgrade note in
[docs/install.md](../install.md#upgrade-notes).

**Before you upgrade:** take a database backup (v1.3 runs twenty migrations), read
[The master switch now covers memories](#the-master-switch-now-covers-memories), and decide whether
you want the in-cluster embedding service, which the chart now runs by default
([Chart changes](#chart-changes)).

## What v1.3 adds

- **Memories beside Notes.** My memory (`/me/memory`, the one memory icon in the top bar) has two
  tabs: **Memories** (short statements: facts, preferences, conventions, definitions, decisions)
  and **Notes** (the Markdown files as before). Memories live in four places: a person's own in
  one workspace, a person's **portable preferences** that follow them into every workspace, the
  **workspace's** shared memories and the **site's** memories. Every edit is versioned with Undo.
- **Learn from this chat.** The author of a conversation asks Kobe to suggest memories from it
  (**+** › Memory › Learn from this chat, `/learn`, `/learn all`, Ctrl/Cmd+Shift+L). A learning
  model reads the new messages and its suggestions land in **To review**; nothing is saved until
  the person saves, edits or dismisses each one. Facts about work stay in their workspace; only
  preferences may follow the person. A workspace or Site suggestion needs a quote from the
  person's own words.
- **To review, proposals and curators.** A member who may not write workspace memories
  **proposes** one; the workspace's curators (Team admins and the new **memory stewards**) approve,
  send back or dismiss it on the Team console's **Memory** page. Readers of a project conversation
  can **suggest** a line for the project's notes; project editors decide.
- **Site proposals.** A member or curator proposes a memory to the Site with a justification; a
  Team admin of that workspace confirms it before anything leaves the workspace; Site admins and
  Site memory stewards approve, merge, reject or request changes (at most three rounds). The
  person who proposed or confirmed a proposal never decides it.
- **Site Policy.** Site admins mark Site memories as **Policy** (at most 25 rules, 2 KiB). Policy
  reaches every run in every workspace, first, and a memory that contradicts it needs an audited
  **Save anyway**.
- **Checks before every save.** Secrets are refused at every scope; instruction-like text,
  personal data, unreachable links and near-duplicates are warnings. Memory never changes an
  agent's tools, approvals or egress: the agent reads memories, it has no tool that writes them.
- **Recall and Open in Memory.** The agent's `recall {query}` finds saved memories;
  `show_memory_item` shows the person an **Open in Memory** chip, so "forget that" is one click
  (archive, with Undo).
- **Quality and the Learn nudge.** Team and Site consoles get a **Quality** tab (queue health, how
  often each memory reached a run and drew a thumbs down, Learn's pass numbers), and the dot on the
  composer's **+** button pulses once when a conversation has enough new messages, or a
  correction, to learn from. It never starts learning by itself.
- **Search by meaning (optional).** Memory search matches words (full-text plus trigram, with a
  little weight for recency). With pgvector in the site's Postgres and an embedding model chosen,
  it also matches meaning, and both the per-message picks and `recall` rank the two together.
  Without either, search is keyword only and nothing else changes.
- **Agents' memory setting.** Each published agent version has **All memory**, **Notes only** or
  **Off**. A run always uses the person's own memory, never the agent owner's.
- **Retention, holds and break-glass.** A Site-wide legal hold for Site memories, Site-level
  break-glass (two Site admins) to read one person's portable preferences, offboarding after 30
  days, and memories in the personal data export.
- **Admin tools.** The Kobe admin MCP gains read-only memory tools; `team_memory_get` /
  `team_memory_set` cover every workspace memory setting.

## The master switch now covers memories

**Allow memory** (`site_settings` key `memory.enabled` on the Site console's **Settings ›
Memory**, and the workspace's **Allow memory** in **Workspace settings › Memory**) was the switch
for Notes. In v1.3 it is the master switch for **Notes and Memories**: where it is off, at the site
or in a workspace, that workspace has no notes **and** no memories, whatever the new switches say.

What this means for a site after the upgrade:

| Before the upgrade                       | After the upgrade                                                                                                                                                                                  |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Allow memory **on** (site and workspace) | Notes work as before. Memories are **on**: every new switch reads as on until an admin turns it off. Learn from this chat still needs a learning model (below).                                    |
| Allow memory **off** in a workspace      | That workspace keeps no notes, as before, and now gets **no memories** either (no personal, portable, workspace or Site memories, no Learn, no proposals). **Site Policy still reaches its runs.** |
| Allow memory **off** on the site         | No notes and **no memories anywhere**, and **no Site Policy** either: the site's own Allow memory switch is the only one that stops Policy.                                                        |
| You want Notes on but memories off       | Leave Allow memory on and turn **Allow memories** off (site or workspace). Notes keep working.                                                                                                     |

Turning any switch off stops its use from the next run on and deletes nothing; turning it back on
brings every note and memory back. An agent version set to **Notes only** gets notes and no
memories; **Off** gets neither. Site Policy reaches its runs whatever the setting.

## New switches and settings

Every switch is on unless an admin turns it off, and a switch that exists at both levels works only
while it is on at both. Turning one off deletes nothing.

| Switch                                    | Where           | Default | What it does                                                                                           |
| ----------------------------------------- | --------------- | ------- | ------------------------------------------------------------------------------------------------------ |
| Allow memory                              | site, workspace | on      | The master switch: Notes **and** Memories (widened in v1.3, above)                                     |
| Allow project notes                       | site, workspace | on      | Project notes, as before; needs Allow memory                                                           |
| Allow memories                            | site, workspace | on      | Memories in runs, My memory's Memories tab; needs Allow memory                                         |
| Workspace memories                        | workspace       | on      | The workspace's shared memories, curated on the Team console's Memory page                             |
| Site memories reach this workspace's runs | workspace       | on      | Site memories in this workspace's runs (Site Policy reaches them either way)                           |
| Portable preferences                      | site            | on      | Preferences that follow a person into every workspace                                                  |
| Learn from this chat                      | site, workspace | on      | Members may ask Kobe to suggest memories from their conversations                                      |
| Nudge to learn                            | site            | on      | The pulse on the composer's + button                                                                   |
| Members may propose to the Site           | site, workspace | on      | Workspace memories may be proposed to the Site (a Team admin confirms first); needs Workspace memories |

Site memory settings (Site console › Settings › Memory; stored in the `memory.settings` key, read
field by field over these defaults, so a site that never saves them keeps the defaults):

| Setting                        | Default                                                                                                              |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| Learning model                 | **none**: Learn is unavailable until a Site admin chooses one                                                        |
| Embedding model                | **none**: search is keyword only until a Site admin chooses one                                                      |
| Memory placement               | with each message; held set re-picked every 20 messages                                                              |
| Context budget                 | 8 KiB (4 to 16)                                                                                                      |
| Scope limits                   | 300 per person per workspace, 50 portable per person, 1,000 per workspace, 1,000 on the site                         |
| Versions kept per memory       | 50                                                                                                                   |
| Stale after / Not used after   | 90 days / 90 days (review flags only; nothing is removed)                                                            |
| Retention of archived memories | 365 days (portable and Site memories; workspaces follow their own retention period)                                  |
| Rate limits                    | 10 learning passes per hour, 30 saves per minute per person (and at most 20 passes per person per workspace per day) |

A workspace may set its own learning model (from the models it has enabled). Learn never falls
back to another model: with no learning model, or one the workspace has not enabled, Learn says so
and does not run. Learning passes go through the model gateway with the purpose `memory_learn`, are
charged to the member who started them, and are refused once that member's budget is used up.

## Chart changes

- **`embeddings.local.enabled: true` (new, on by default).** The chart runs a small CPU embedding
  service: llama.cpp's `llama-server` (pinned by tag and digest) serving **nomic-embed-text v1.5**
  (768 dimensions, about 270 MB), one replica requesting 1 CPU / 1 GiB, limited to 2 CPUs / 1 GiB,
  with a 1 Gi PVC for the model file. Only Bifrost's pods may connect to it; the server registers
  it in the gateway as the keyless provider `kobe-local`, so the model is
  `kobe-local/nomic-embed-text`. Running it does not turn on search by meaning: a Site admin still
  chooses the embedding model (below).
  - **First start downloads the model** from its pinned URL (`model.download: true`), so the pod
    may reach DNS and public HTTPS. Set `embeddings.local.model.download: false` after the first
    start to remove that egress; the file stays on the PVC and its sha256 is checked on every
    start.
  - **Air-gapped:** `model.download: false` and `persistence.existingClaim` pointing at a claim
    that already holds the GGUF file.
  - **Turn it off:** `embeddings.local.enabled: false`. The deployment, PVC and network policy are
    not rendered and the `kobe-local` provider leaves the gateway on the next sync.
  - **Use an external model instead:** turn it off and add the embedding model as a provider in
    the Site console (**Models and providers**): an Ollama server on your network (with
    `allow_private_network` and a `bifrost.networkPolicy.extraEgress` rule to it) or a hosted
    provider with a site key. Then choose it as the embedding model.
  - Values: `embeddings.local.{image, model.{name, file, download, url, sha256}, contextSize,
threads, persistence.{enabled, size, storageClass, existingClaim}, networkPolicy.extraEgress,
resources}`. See [Embeddings (in-cluster CPU model)](../install.md#embeddings-in-cluster-cpu-model).
- **pgvector (optional, not a chart value).** Vectors are stored with the pgvector extension in the
  site's Postgres. Kobe's migration role is not a superuser, so install the extension's package for
  your Postgres 17 and run `CREATE EXTENSION vector;` once as a superuser in Kobe's database; the
  next upgrade adds the vector columns. Without it the migration logs a notice and memory search
  stays keyword only. See [Vector search for memory](../install.md#vector-search-for-memory-pgvector).
- No other chart value changes for v1.3.

## Migrations

v1.3 adds migrations `0216` to `0235`. They run in the chart's migration Job before the new pods
start (the usual `pre-upgrade` hook), so there is nothing to run by hand. **Take a database backup
first** ([backup and restore](../backup-restore.md)); there are no down migrations. Follow the Job's
log (`kubectl logs -f job/<release>-migrate`) for its notices, for example whether pgvector was
found.

- `0216`–`0227` (Phase A): the memory item tables and their versions, memory stewards, memory
  notification kinds, version pruning, the agent version memory setting, the Site-wide legal hold
  and Site-level break-glass.
- `0228`–`0235` (Phases B to D): learning passes, suggestions, dismissals, watermarks and
  workspace proposals (`0228`, `0229`); optional vector columns (`0230`, a no-op without
  pgvector); readers' project note suggestions (`0231`, `0232`); Site proposals (`0233`), and a
  guard that keeps a workspace's Site proposals when a workspace delete is attempted (`0234`); a
  separate `stale` state for project suggestions whose conversation left the project (`0235`).

All of them add empty tables, columns or check values except `0235`, which re-labels existing
project suggestions closed before their expiry as `stale`. `0220` and `0235` hold an exclusive lock
on `notifications` while they re-check it (well under a second at typical sizes), so the bell
waits for them. Every new team table has row-level security on `kobe.team_id` like every other.

**Rolling back.** The previous release ignores the new tables, columns and settings. One exception:
it cannot read a Site **memory steward** grant, so remove those grants in **Site roles** before a
`helm rollback` past v1.3, or roll forward instead.

## Privacy: the team wall

- **Only a statement and its justification cross to the Site.** A Site proposal carries its
  statement, kind, justification, source workspace and the people who proposed and confirmed it.
  The conversation, quotes, evidence, notes and the learning model's reasoning never leave the
  workspace; the Site proposals table has no column for them.
- **Facts stay in their workspace.** Only preferences can be portable; Learn never suggests a
  portable fact.
- **Site audit and SIEM show Site-safe details only.** The Site console's audit view and SIEM
  forwarding (syslog/OTLP) carry a workspace event with allow-listed fields only: thread, entry,
  run, learning pass, suggestion, tool call and approval ids, and the record of a person acting
  through an agent, are left out (the view fails closed on any field not on the list). Site-level
  events are unchanged. The full record stays in each workspace's own audit log (Workspace console
  › Audit), and the Site console's audit page says so. See [docs/audit-log.md](../audit-log.md).
- **Embeddings.** Choosing an embedding model sends members' messages (up to 4,000 characters) and
  memory statements to that model's provider through the gateway. The in-cluster model keeps them
  in the cluster.
- **Portable preferences** are readable only by their owner, or by a Site admin under a time-boxed
  break-glass grant a second Site admin approved; the person is emailed and every read is audited
  in the site and in each of their workspaces.

## Retention

Kobe never deletes a live memory and never archives one for you. What goes:

- Suggestions in To review that nobody acted on: after **14 days** (an expired suggestion is not a
  dismissal).
- Workspace proposals, readers' project note suggestions and Site proposals still waiting: expire
  after **30 days** (a request for changes does not restart the clock); one notification each.
- A learning pass's record, with its suggestions and the **decided** proposals and project
  suggestions made from it: when it is older than the workspace's retention period (never while the
  workspace keeps conversations forever, never while something is still waiting).
- Archived memories and old versions: after the workspace's retention period (portable and Site
  memories: the Site's 365-day window). The current version and any version a run used stay.
- A person's own memories in a workspace: 30 days after they leave it. Workspace and Site memories
  they wrote stay.
- Legal holds (on a person, a workspace or the whole site) suspend all of this.

## Known limits

- The **Merge into existing…** picker on a Site proposal loads the first 100 Site memories, with no
  search. Workspace-side lists show "Showing N of M" past 100.
- Site curators who belong to no workspace get no bell notices for Site proposals; they see the
  Site queue. A Team admin promoted while a step waits gets no reminder for that step.
- Learn's nudge threshold is fixed at about 10 messages.
- An archived memory's note can stay in earlier messages of a conversation until its sandbox
  restarts; the next message no longer gets it.
- The in-cluster embedding service has no API key; only its network policy (Bifrost's pods) keeps
  other pods out.
- Kobe has no way to delete a workspace today; the database refuses to delete one that ever
  proposed something to the Site.

## Upgrade steps

1. **Back up** the database ([backup and restore](../backup-restore.md)).
2. **Decide on embeddings.** Keep `embeddings.local.enabled: true` (the default; the pod downloads
   the model once on first start), set `model.download: false` with a preloaded claim
   (air-gapped), or set `embeddings.local.enabled: false` (no service; use an external model or
   keyword search only). For search by meaning, install pgvector in the site's Postgres and run
   `CREATE EXTENSION vector;` before upgrading.
3. **Check the master switch** ([above](#the-master-switch-now-covers-memories)): where Allow
   memory is off, memories will be off too. To keep Notes and leave memories off, turn **Allow
   memories** off instead after the upgrade.
4. **Upgrade** with your values file as for any release (`helm upgrade <release> ... -f
<your values> --wait`) and follow the migration Job's log.
5. **After the rollout**, in Site console › Settings › Memory:
   - choose a **learning model** (Learn from this chat is unavailable until you do) and make sure
     workspaces have it enabled, or let team admins choose their own;
   - choose an **embedding model** (for example `kobe-local/nomic-embed-text`) and press **Build
     vectors**: nothing is embedded automatically after an upgrade;
   - review the switches and limits above.
6. **Name memory stewards** if you want curators besides admins: Site memory stewards in **Site
   roles**, Workspace memory stewards on each Team console.
7. If you kept the in-cluster embedding service with download on, set
   `embeddings.local.model.download: false` after its first start and upgrade again.
