# Rate limits

This page lists every rate limit in Kaiju as the code stands on `main`. A rate limit here is
anything that caps how often or how much something may happen in a time window, plus
concurrency caps that answer "try later" rather than a final refusal. Body-size limits,
pagination limits, retention periods and pure retry/backoff logic are out of scope. Spending
budgets are covered in one line under [Models](#models); for the feature itself see
`docs/guide/models.md` ("Budgets") and `docs/guide/admin/team-admin.md`.

Every value below was read from code; `path:line` points at the definition or the check.

## How limits are built

There is no Redis. Kaiju uses five kinds of limiter:

- **Postgres fixed window (`takeRateLimit` / `hitRateLimit`, `packages/db/src/rate-limit.ts:75`,
  used by the server through `services/server/src/rate-limit.ts`: `hitRateLimit`, `checkRateLimit`,
  `countRateLimitHit`).** One atomic upsert on the `kobe_rate_limits` table per hit, key prefixed
  `kobe:`. The window starts at the first hit and resets when a hit arrives after `windowMs`. All
  server replicas share the counter. Kaiju's limits use their own table, separate from the sign-in
  library's. Each row records when its window ends; a hit that starts a new window deletes up to 100
  expired rows (`pruneExpiredRateLimits`), so the table holds about the live windows only.
  `checkRateLimit` also reports when the window ends: the limits added by KOBE-813
  (`OPERATION_LIMITS` in `services/server/src/operation-limits.ts`, one place for all of them)
  answer 429 `{code: "rate_limited", message}` with `Retry-After` in seconds. Older Postgres-window
  limits send no `Retry-After`, except SCIM's and the per-account sign-in throttle's. Time comes
  from the database clock inside the statement (KOBE-810), so server replicas whose clocks disagree
  still share one window and none prunes a row early. The per-account sign-in throttle passes its
  own server time instead, because its slot and marker statements use the same clock.
- **Postgres refilling bucket (`takeRateBucket`, `packages/db/src/rate-limit.ts:156`, KOBE-810).**
  The same table and one atomic statement per request, as GCRA: the row stores the bucket's
  theoretical arrival time (`window_start` in microseconds, `expires_at` the same instant in ms;
  `count` is 1 when the last request was admitted, 0 when refused). It behaves like an in-memory
  token bucket of `burst` refilled at `perSecond`: refused requests are not charged, and a refusal
  knows when one request is available again. The refill interval is rounded up to a whole
  microsecond, so the sustained rate is at most 0.02 % below the setting (at 10,000 a minute).
  Time comes from the database clock inside the statement, so replicas with skewed clocks share
  one bucket. It is shared by every replica of the server and the model gateway (both connect as
  the app role); a full bucket's row is pruned like an expired window, in the background (at most
  every 10 s per replica and limit), never on the request. Used by the member per-minute model
  rate and the two MCP App limits.
- **Better Auth's own limiter** for `/api/auth/*`, configured in
  `services/server/src/auth/auth.ts:181` with `storage: "database"`. It uses its own
  `rate_limits` table, keyed by client IP and path. It answers 429
  `{"message":"Too many requests. Please try again later."}` with an `X-Retry-After` header
  (seconds), not `Retry-After`.
- **In-memory token bucket (`createRateLimiter`, `services/server/src/sandbox/rate-limit.ts:50`)**
  and similar buckets in mcp-proxy, egress-proxy and the model gateway. Each pod has its own
  buckets. Chart defaults: server 2 replicas, model gateway 2, mcp-proxy 1, egress-proxy 1.
- **Counted caps.** Counts in Postgres, such as open requests or passes in the last 24 hours,
  or in-memory slot counters per pod, such as open streams or calls in flight.

The State column gives each limit's storage and scope. "Postgres" means it is shared by every
replica and survives restarts: the limit is exact across replicas. "Memory (pod), per replica"
means the state lives in one pod and is lost on restart: with N replicas a caller can get up to N
times the value if their requests spread over pods. "Memory (sandbox), per connection" and
"Browser" limits live in the client and do not depend on replicas.

**Per replica by design (KOBE-810).** Every in-memory limit was reviewed. Three moved to Postgres
because they are product numbers or guard upstream calls under a member's credentials: the member
per-minute model rate, MCP App tool calls and opening MCP App cards. The rest stay in memory on
purpose. They protect the pod itself or what sits behind it (sockets, memory, worker threads, the
database pool, the Kubernetes API, an identity provider), many count per connection or per stream
that lives on one pod, and several run before authentication or before any database read so that
a hostile client cannot turn retries into Postgres load. A database write per frame, file
operation or pre-auth socket would add load to exactly the paths they shield. Their values are not
divided by the replica count: Kubernetes balances per TCP connection and keep-alive clients (the
sandbox's model, MCP and sync clients) stay on one pod, so a divided value would refuse a
legitimate sandbox at a fraction of its allowance. Model spend is capped across replicas by the
budget reservations regardless. The egress proxy's git limits (KOBE-763: requests, distinct repositories
looked up, concurrent requests per sandbox) and the server's git decision limit follow the same
rule: a sandbox's git traffic stays on the proxy pod that holds its tunnel.

The client IP used by IP-keyed limits comes from `X-Forwarded-For`, read through the trusted
proxy list: env `KAIJU_TRUSTED_PROXIES`, Helm `auth.trustedProxies`, chart default the k3s pod
CIDR (`charts/kobe/templates/_helpers.tpl:209`).

**When no client IP can be resolved** (the trusted proxy list doesn't match the proxies in front
of the server, or they send no `X-Forwarded-For`), Better Auth puts every such client in one
bucket per path, so one caller can use up a sign-in limit for everyone in it. Kaiju keeps that
library behaviour but reports it (KOBE-812): a start-up warning when `KAIJU_TRUSTED_PROXIES` is
empty, a log warning (once per replica and source) on the first such request, and a notice on Site
console › Users for a day after the last sighting (`GET /v1/site/users/sign-in-protection`,
`unknownClientIp`; sightings in `kobe_rate_limits` key `kobe:unknown-client-ip`, no address
stored; `services/server/src/auth/client-ip-watch.ts`). The per-account sign-in throttle below
does not depend on the client IP. SCIM failed authentications without an IP are counted per
provider slug (`scim-auth-fail:no-ip:<slug>`) instead of one shared `unknown` bucket; a request
with a valid token never meets that limit.

## Models

The model gateway shim (`services/model-gateway`) checks its limits before contacting Bifrost.
Error bodies follow the caller's SDK format (OpenAI `error.code`, Anthropic `error.type`,
Gemini `reason`). Spending budgets (402 `budget_exhausted` etc.) are a separate feature: see
`docs/guide/models.md`.

**Every model request needs Postgres (KOBE-810).** The member per-minute rate is one upsert per
request (about 2.3 ms on the LAN), so a Postgres outage now stops model calls for every Workspace.
Before, a Workspace without budget lines kept working through a short outage on cached state;
Workspaces with budgets already needed the database for the reservation. The gateway runs the
rate check on its own pool (2 connections per replica by default: `KAIJU_MODEL_GATEWAY_RATE_POOL_MAX`,
Helm `modelGateway.database.ratePoolMax`) with a 2 s acquire timeout and a 2 s
statement timeout, so a slow or saturated database refuses a request within about 2 s, not after
the main pool's 10 s acquire timeout (deliberate there: reservations and principal loads may wait
through a short spike). The refusal is 503 `rate_limit_unavailable` with `Retry-After: 2`. The
sandbox retries it at most 8 times within 60 s per request (see
[Upstream 429 handling](#upstream-429-handling)), then the run fails with `model_unavailable`.

## Chart and ingress

The chart can add a per-client-address limit at the ingress, off by default:
`ingress.rateLimit.enabled: true` renders a Traefik `Middleware` (`traefik.io/v1alpha1`) with
`average` requests per `period` and `burst` (defaults 100 per 1s, burst 300) and attaches it to
every route of the Kaiju Ingress. Event streams (`/v1/runs/<id>/events`, `/v1/workspace/events`,
`/v1/workspace/changes`, `/v1/skill-evals/<id>/events`) go through a second Ingress with a
separate budget (`ingress.rateLimit.streams`, defaults 60 per 1m, burst 120; `enabled: false`
leaves them unlimited), so stream reconnects do not spend the page budget; open streams are never
cut. The sandbox WebSocket and the MCP proxy's routes never pass the ingress. Over the limit
Traefik answers 429 before the request reaches Kaiju; the application limits above still apply
behind it. It needs Traefik v3 (k3s 1.32 or later; the chart refuses older clusters unless
`assumeTraefikV3: true`). **Before enabling on k3s**, set the Traefik Service to
`externalTrafficPolicy: Local`: with the default `Cluster`, ServiceLB hides client addresses and
every user shares one budget per node. Leave `ingress.rateLimit.ipStrategy` empty unless an L7
proxy in front of Traefik always adds a trusted `X-Forwarded-For`; with it set and no usable
address, the whole Site shares one budget. While no limit is configured the Site console shows
Site admins an information notice; `ingress.rateLimit.external: true` declares an edge limit of
your own and hides it. See [Rate limit at the ingress](install.md#rate-limit-at-the-ingress-optional).

## Upstream 429 handling

- **Model providers.** Bifrost does not retry (`max_retries: 0`,
  `services/server/src/models/bifrost-admin.ts:189`). The gateway shim does not retry a 429 and
  relays the error body (up to 64 KiB), status and `retry-after` header unchanged
  (`services/model-gateway/src/gateway/forward.ts:168`; `services/model-gateway/src/headers.ts:35`).
- **In the sandbox.** The agent's model provider retries 429, 502, 503, 504 and 529 and the
  shim's busy codes (`rate_limited`, `too_many_concurrent_calls`, `too_many_bytes_in_flight`,
  `model_gateway_resyncing` …). It makes up to 8 attempts within 60 s, waits `Retry-After`
  (numeric seconds, capped at 30 s) or backs off 1, 2, 4, 8, 16 s, and never retries once
  output has streamed (`services/sandbox-agent/src/kobe-models/provider.ts:43`;
  `services/sandbox-agent/src/kobe-models/errors.ts:28`). When it gives up after a 429, the run
  fails with `model_throttled`, shown as "The model is rate-limited right now. Wait a moment and
  try again." (`services/sandbox-agent/src/kobe-models/errors.ts:125`;
  `services/server/src/runs/failure-codes.ts:65`). When the gateway cannot reach Postgres to count
  the member's per-minute rate it refuses with 503 `rate_limit_unavailable` (fail closed); the
  agent retries it like any 503, and if Postgres stays down the run fails with
  `model_unavailable`, shown as "The model gateway is unavailable right now. Try again in a
  moment." (`services/server/src/runs/failure-codes.ts:66`).
- **Server-made model calls** (titles, compaction, embeddings) do not retry. A 429 becomes a
  `ServerCallError` (`services/server/src/models/gateway-client.ts:326`;
  `services/server/src/models/embedding-client.ts:131`).
- **Workspace sync.** The sandbox's sync client retries 429 and 503 up to 5 times, waiting
  `Retry-After` or 200 ms doubling, capped at 5 s, with jitter. Uploads are not retried. A sync
  step that keeps getting 429 is retried as a whole after 5 minutes
  (`services/sandbox-agent/src/workspace/client.ts:209`;
  `services/sandbox-agent/src/workspace/sync/state.ts:39`).
- **MCP connectors.** mcp-proxy has no retry on upstream 429s. The upstream answer goes back to
  the agent as the tool result or error.
- **Web app.** It shows the server's `message` for a 429, or "Too many requests. Try again
  later." if there is none (`apps/web/lib/api/client.ts:117`). It never reads `Retry-After`.

## Gaps and observations

1. **The edge limit is off by default.** The chart can ship a Traefik limit (see
   [Chart and ingress](#chart-and-ingress)) but does not enable it. Until it is on, or declared
   with `ingress.rateLimit.external: true`, anything not covered here is unlimited at the
   ingress, and the Site console shows Site admins an information notice.
2. **Limits added by KOBE-813 are constants.** The ten limits in `OPERATION_LIMITS` are not
   configurable.
   - `POST /v1/workspace/wake` and `POST /v1/workspace/sync` are not in the OpenAPI document (the
     whole `/v1/workspace/*` files area is missing there, and the coverage test does not mount
     it), so their 429 is listed only here.
   - Scheduled runs are outside the message limit. What bounds them: 10 active schedules per
     member, no schedule more often than every 15 min, and budgets. Editing a schedule's time
     after each fire could reach about one run a minute per schedule (10 a minute in all).
     Skill evals are bounded by the eval concurrency and the eval budget.
   - Setup is limited per client IP. With wrong `auth.trustedProxies` every visitor can look like
     one address (or the shared `unknown` bucket), so anyone could keep setup refused; the token
     can't be guessed either way. Recovery is in `docs/install.md` (fix the proxies, or post the
     setup straight to the server through `kubectl port-forward`).
   - A message resent with the same `Idempotency-Key` (after a network error) counts again,
     although the server answers it with the first run.
3. **The Kaiju admin limits can't be changed from the product.** `kobe_mcp.reads_per_minute` and
   `kobe_mcp.writes_per_hour` are read from `site_settings`, but no route or console page writes
   them.
4. **Retry hints are inconsistent.**
   - Postgres-window 429s from before KOBE-813 send no `Retry-After` (SCIM and the per-account
     sign-in throttle excepted); the MCP App
     buckets send none either (the model gateway's per-minute bucket does).
   - Better Auth sends `X-Retry-After`.
   - mcp-proxy's in-flight 429 and the egress-proxy 429 send none.
   - The web app ignores `Retry-After` everywhere; it shows the server's sentence instead.
5. **Response shapes are inconsistent.** MCP App call 429s use a nested
   `{error:{code,message}}` body, unlike the rest of the API. Kaiju admin limits arrive as a
   denied tool call, not HTTP 429.
6. **Shared buckets.**
   - Site and Workspace audit exports share one `audit-export:<user>` bucket.
   - One `skill-upload` bucket covers uploads, imports, copies, saves and the agent's draft
     tool.
   - `skill-manifest` is shared by draft manifests and promotions.
   - Server-made model calls draw on the member's per-minute model rate.
   - One `git-host-calls:<user>` bucket covers connecting, testing without saving, replacing a
     credential and Check now on git connections (KOBE-760).
7. **Sandbox-wire limits are fixed.** Frame and byte rates, upgrade rate and connection count
   have no env var or Helm value (`services/server/src/sandbox-wire/constants.ts:140`). The
   server's git decision limit on its internal listener (`GIT_DECIDE_RATE`, KOBE-763) is fixed
   too; the egress proxy's git limits are configurable.
8. **Unclear.** What a member sees when the Workspace's Kubernetes ResourceQuota (`sandbox.teamQuota`) stops a sandbox pod was not traced. It surfaces as a sandbox start failure, not as a 429.
