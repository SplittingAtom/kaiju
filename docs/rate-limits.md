# Rate limits

This page lists every rate limit in Kobe as the code stands on `main`. A rate limit here is
anything that caps how often or how much something may happen in a time window, plus
concurrency caps that answer "try later" rather than a final refusal. Body-size limits,
pagination limits, retention periods and pure retry/backoff logic are out of scope. Spending
budgets are covered in one line under [Models](#models); for the feature itself see
`docs/guide/models.md` ("Budgets") and `docs/guide/admin/team-admin.md`.

Every value below was read from code; `path:line` points at the definition or the check.

## How limits are built

There is no Redis. Kobe uses four kinds of limiter:

- **Postgres fixed window (`hitRateLimit`, `services/server/src/rate-limit.ts:20`).** One
  atomic upsert on the `kobe_rate_limits` table per hit, key prefixed `kobe:`. The window starts
  at the first hit and resets when a hit arrives after `windowMs`. All server replicas share the
  counter. Kobe's limits use their own table, separate from the sign-in library's. Each row
  records when its window ends; a hit that starts a new window deletes up to 100 expired rows
  (`pruneExpiredRateLimits`), so the table holds about the live windows only. None of these
  429s sends `Retry-After`, except SCIM's.
- **Better Auth's own limiter** for `/api/auth/*`, configured in
  `services/server/src/auth/auth.ts:168` with `storage: "database"`. It uses its own
  `rate_limits` table, keyed by client IP and path. It answers 429
  `{"message":"Too many requests. Please try again later."}` with an `X-Retry-After` header
  (seconds), not `Retry-After`.
- **In-memory token bucket (`createRateLimiter`, `services/server/src/sandbox/rate-limit.ts:50`)**
  and similar buckets in mcp-proxy, egress-proxy and the model gateway. Each pod has its own
  buckets: with N replicas a caller can get up to N times the limit if requests spread across
  pods. Chart defaults: server 2 replicas, model gateway 2, mcp-proxy 1, egress-proxy 1.
- **Counted caps.** Counts in Postgres, such as open requests or passes in the last 24 hours,
  or in-memory slot counters per pod, such as open streams or calls in flight.

"Memory (pod)" in the tables below means the state is per replica and lost on restart.
"Postgres" means it is shared by every replica and survives restarts.

The client IP used by IP-keyed limits comes from `X-Forwarded-For`, read through the trusted
proxy list: env `KOBE_TRUSTED_PROXIES`, Helm `auth.trustedProxies`, chart default the k3s pod
CIDR (`charts/kobe/templates/_helpers.tpl:209`).

## Chart and ingress

The chart can add a per-client-address limit at the ingress, off by default:
`ingress.rateLimit.enabled: true` renders a Traefik `Middleware` (`traefik.io/v1alpha1`) with
`average` requests per `period` and `burst` (defaults 100 per 1s, burst 300) and attaches it to
every route of the Kobe Ingress. Event streams (`/v1/runs/<id>/events`, `/v1/workspace/events`,
`/v1/workspace/changes`, `/v1/skill-evals/<id>/events`) go through a second Ingress with a
separate budget (`ingress.rateLimit.streams`, defaults 60 per 1m, burst 120; `enabled: false`
leaves them unlimited), so stream reconnects do not spend the page budget; open streams are never
cut. The sandbox WebSocket and the MCP proxy's routes never pass the ingress. Over the limit
Traefik answers 429 before the request reaches Kobe; the application limits above still apply
behind it. It needs Traefik v3 (k3s 1.32 or later; the chart refuses older clusters unless
`assumeTraefikV3: true`). **Before enabling on k3s**, set the Traefik Service to
`externalTrafficPolicy: Local`: with the default `Cluster`, ServiceLB hides client addresses and
every user shares one budget per node. Leave `ingress.rateLimit.ipStrategy` empty unless an L7
proxy in front of Traefik always adds a trusted `X-Forwarded-For`; with it set and no usable
address, the whole Site shares one budget. While no limit is configured the Site console shows
Site admins an information notice; `ingress.rateLimit.external: true` declares an edge limit of
your own and hides it. See [Rate limit at the ingress](install.md#rate-limit-at-the-ingress-optional).

## Upstream 429 handling

- **Model providers.** Bifrost does not retry (`max_retries: 0`,
  `services/server/src/models/bifrost-admin.ts:189`). The gateway shim does not retry a 429 and
  relays the error body (up to 64 KiB), status and `retry-after` header unchanged
  (`services/model-gateway/src/gateway/forward.ts:168`; `services/model-gateway/src/headers.ts:35`).
- **In the sandbox.** The agent's model provider retries 429, 502, 503, 504 and 529 and the
  shim's busy codes (`rate_limited`, `too_many_concurrent_calls`, `too_many_bytes_in_flight`,
  `model_gateway_resyncing` …). It makes up to 8 attempts within 60 s, waits `Retry-After`
  (numeric seconds, capped at 30 s) or backs off 1, 2, 4, 8, 16 s, and never retries once
  output has streamed (`services/sandbox-agent/src/kobe-models/provider.ts:43`;
  `services/sandbox-agent/src/kobe-models/errors.ts:28`). When it gives up after a 429, the run
  fails with `model_throttled`, shown as "The model is rate-limited right now. Wait a moment and
  try again." (`services/sandbox-agent/src/kobe-models/errors.ts:125`;
  `services/server/src/runs/failure-codes.ts:65`).
- **Server-made model calls** (titles, compaction, embeddings) do not retry. A 429 becomes a
  `ServerCallError` (`services/server/src/models/gateway-client.ts:326`;
  `services/server/src/models/embedding-client.ts:131`).
- **Workspace sync.** The sandbox's sync client retries 429 and 503 up to 5 times, waiting
  `Retry-After` or 200 ms doubling, capped at 5 s, with jitter. Uploads are not retried. A sync
  step that keeps getting 429 is retried as a whole after 5 minutes
  (`services/sandbox-agent/src/workspace/client.ts:209`;
  `services/sandbox-agent/src/workspace/sync/state.ts:39`).
- **MCP connectors.** mcp-proxy has no retry on upstream 429s. The upstream answer goes back to
  the agent as the tool result or error.
- **Web app.** It shows the server's `message` for a 429, or "Too many requests. Try again
  later." if there is none (`apps/web/lib/api/client.ts:117`). It never reads `Retry-After`.

## Gaps and observations

1. **In-memory limits multiply with replicas.** Every "Memory (pod)" limit is per replica. The
   member per-minute model rate is enforced per gateway replica (2 by default), so up to twice
   the value passes the shim. Bifrost's per-key window is the real cap, and its 429 goes back to
   the sandbox in Bifrost's format.
2. **The gateway's per-sandbox bucket map is cleared, not pruned.** Once more than 10,000 keys
   exist, `buckets.clear()` refills everyone's bucket (`services/model-gateway/src/limits.ts:88`).
3. **The edge limit is off by default.** The chart can ship a Traefik limit (see
   [Chart and ingress](#chart-and-ingress)) but does not enable it. Until it is on, or declared
   with `ingress.rateLimit.external: true`, anything not covered here is unlimited at the
   ingress, and the Site console shows Site admins an information notice.
4. **Sign-in is limited only per IP.** Sign-in, change password and two-factor are 3 per 10 s
   per IP and path. There is no per-account lockout, so a distributed guess against one account
   is not slowed. Passkey endpoints fall under the general 100 per 10 s. When no client IP can be
   resolved (trusted proxies wrong), Better Auth puts every client in one shared bucket per path.
   SCIM failures fall into an `unknown` bucket the same way.
5. **No rate limit found on:**
   - run submission across conversations (only 1 active and 25 queued per conversation);
   - compaction and branch summary (budget only);
   - uploads (`POST /v1/uploads`: size and storage quota only);
   - schedule creation (cap of 10 active only);
   - SCIM token creation (2 live tokens only);
   - sandbox wake or start (apart from notebook kernel starts);
   - answer feedback;
   - the setup token before setup is finished (`services/server/src/routes/setup.ts`).
6. **The Kobe admin limits can't be changed from the product.** `kobe_mcp.reads_per_minute` and
   `kobe_mcp.writes_per_hour` are read from `site_settings`, but no route or console page writes
   them.
7. **Retry hints are inconsistent.**
   - Postgres-window 429s send no `Retry-After` (SCIM excepted).
   - Better Auth sends `X-Retry-After`.
   - mcp-proxy's in-flight 429 and the egress-proxy 429 send none.
   - The web app ignores `Retry-After` everywhere.
8. **Response shapes are inconsistent.** MCP App call 429s use a nested
   `{error:{code,message}}` body, unlike the rest of the API. Kobe admin limits arrive as a
   denied tool call, not HTTP 429.
9. **Shared buckets.**
   - Site and Workspace audit exports share one `audit-export:<user>` bucket.
   - One `skill-upload` bucket covers uploads, imports, copies, saves and the agent's draft
     tool.
   - `skill-manifest` is shared by draft manifests and promotions.
   - Server-made model calls draw on the member's per-minute model rate.
10. **Sandbox-wire limits are fixed.** Frame and byte rates, upgrade rate and connection count
    have no env var or Helm value (`services/server/src/sandbox-wire/constants.ts:140`).
11. **Comment drift.** `services/server/src/apps/call-deps.ts:15` says launches share the app
    call limit, but app card launches use their own `APP_LAUNCH_RATE` bucket.
12. **Unclear.** What a member sees when the Workspace's Kubernetes ResourceQuota (`sandbox.teamQuota`) stops a sandbox pod was not traced. It surfaces as a sandbox start failure, not as a 429.
